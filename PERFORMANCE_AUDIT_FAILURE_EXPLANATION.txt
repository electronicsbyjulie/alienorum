The previous performance audit missed a major serialization problem. Calling that work an exhaustive application audit was not justified by the evidence I collected. The user explicitly requested a thorough review; inspecting a few serialization operations and reducing one allocation did not satisfy that request. The responsibility for that gap is mine.

The 17 recorded findings were real, and the measurements supporting those individual fixes still matter. However, a list of valid findings is not evidence that the review covered the application comprehensively. I treated the completion of my own list as completion of the audit. That was the central process failure.

This explanation describes what I missed, how the methodology allowed it, what the subsequent JSON work demonstrated, and how the replacement audit differs. Its code baseline is the completed fix commit ed050bb on fakestars. The earlier audit and its final state are visible in 4d2983e through fa434be. No proposed frame-rate optimization is implemented by this report.

1. I optimized a serialization operation without auditing the data being serialized.

The earlier PA01 work replaced a complete dump(4) string with direct formatted stream output. In its controlled 100,000-record workload, this lowered peak RSS from 178,820 to 120,608 KiB. That addressed a genuine extra allocation. PA02 also removed repeated serialization of shared ancestors while retaining duplicate-key behavior.

Neither change answered the larger questions: Why does an individual object contain these fields? Which values are inputs, which are derived reports, which are constructor defaults, and which are repeated across thousands of objects? How much space and parsing work does each category consume? Can the loader reconstruct the same state from a smaller representation?

The source already made those questions discoverable. Before the compact-format fix, CelestialObject::to_json wrote a common block of fields for every subclass. Star::to_json added catalog identifiers, WD state, system metadata, provenance, flags, and metallicity measurements. Planet::to_json included classification_evidence. Serialization::save_all assembled the complete document and emitted four-space indentation. I inspected parts of this path but did not inventory its payload.

The resulting audit item was too narrow: remove the extra output string, then verify identical output. It was a useful local optimization, not a serialization audit.

2. I imposed a byte-preservation constraint that was stricter than the user's quality constraint.

Preserving physical state, names, relationships, edit semantics, classification behavior, and compatibility is appropriate. Preserving every redundant field and every indentation space is not equivalent to preserving quality.

I wrote an exact formatted-output regression check for the stream change. That made sense for proving that a narrow change had no unrelated effect, but I then treated the existing representation as a fixed boundary. I should have distinguished two questions: whether streaming preserved the old format, and whether the old format itself was efficient. The first check did not answer the second.

A backward-readable, versioned format can retain the same physical state without retaining identical bytes. The subsequent fix demonstrates this directly. I should have considered that possibility during the original audit instead of accepting the old payload as an untouchable quality requirement.

3. I did not use the actual universe file as a primary workload.

The previous audit used controlled synthetic records to isolate allocation cost, ancestor duplication, and other individual operations. Such workloads are valuable because they can prove an optimization preserves particular behavior. They do not substitute for inspecting a real saved population.

The file examined during the subsequent JSON work contained 126,874 records: 10,000 stars, 19,794 planets, and 97,080 moons. That distribution matters. A benchmark centered on a simple star or a small shared-parent hierarchy underrepresents the cost of planet diagnostics, nested atmospheres, repeated reference frames, and many moons.

The user's current population is larger than the file present earlier in the session, and the local planetary-host setting has changed from 10% to 33.3%. Those facts amplify the problem; they do not excuse the omission. The old format already had the same structural duplication. A thorough audit should have tested population scaling and several planet/moon densities rather than relying on one convenient workload.

The original file was also available locally. Establishing its size, object mix, repeated subobjects, and largest field groups did not depend on GPU access or specialist profiling permissions.

4. I did not separate retained inputs from derived diagnostic output.

classification_evidence was a particularly expensive omission. In the inspected file, compact serialization of that field across the saved population accounted for roughly 81.6 MB, before the surrounding document's indentation. It includes reports about classification decisions, host chemistry, density assumptions, temperatures, and model status.

The classifier uses the actual physical fields and evidence enums; it does not consume the saved diagnostic report as a classification input. The report can be generated again when classification runs. Removing that persisted report does not mean removing metallicity-informed classification, measured/estimated distinctions, or physical evidence.

The WD display profile was another derived output. The important inputs are the retained observed colors or atmosphere/template information, temperature, spectral type, and other actual parameters. Persisting a second human-readable report about the resolved display color was redundant.

This distinction required following readers and callers, not just inspecting writer functions. I failed to complete that data-flow review during the earlier audit.

5. I did not account for shared metadata and inherited serializer fields.

Every generated star carried a full generation-batch description in fictional_origin. In the inspected population, the repeated batch contribution was about 13.2 MB in compact form. The batch is common to thousands of stars. Storing it once is a straightforward normalization opportunity.

fictional_origin also contains useful per-star information: stable identity, component information, age/population metadata, position and motion inputs, and WD atmosphere information for applicable stars. Deleting the whole object would be unsafe. The right question was how to retain its useful state without copying the same batch record into every star.

The same review should have caught default catalog IDs on fictional stars, false flags, empty identifiers, the inherited transparent_clouds field on stars, default WD fields on ordinary stars, duplicated display/original names, and generated stellar_system labels that are exactly reconstructible from identity and component metadata.

Some apparently redundant fields really do affect behavior. Real authored systems, including the Orion systems, retain their metadata. Mass/radius evidence enums affect classification. A zero apparent magnitude is valid, Bayer index zero identifies Alpha, false can clear a previous catalog value, and an absent atmosphere is different from an explicitly airless one. A proper audit would classify these cases, not assume either that every field must remain or that every zero can be deleted blindly.

6. I did not audit the nested readers' copying costs.

Object readers accepted their JSON records by value. A moon passed through the moon, planet, and base-object readers, making repeated copies of the same nested record. Some nested objects were copied again into local variables before being passed onward.

Those copies are visible in the signatures and call chain. The replacement work changed the large object readers to const references and used references for applicable nested records. It also stopped retaining another expanded record for newly imported objects when only replacement objects require that retained data for transactional commit.

The earlier audit concentrated on the writer's extra dump string and omitted this corresponding reader-side cost. That was especially relevant to the user's complaint about slow loading.

7. I missed an expensive estimate that was outside the reported generation timer.

Before ed050bb, generate_fictional_stars set result.elapsed_seconds before formatting every generated world with to_json().dump(4) to estimate save size. It then multiplied one formatted star's size across the star count.

The function's own elapsed_seconds field consequently excluded that serialization tail. An outer timer around the full call could still include it; the earlier audit did use outer timing in some controlled comparisons. The mistake was failing to break down and inspect the entire path, including the estimate, rather than relying on aggregate timings and the existing displayed duration.

The estimate was both expensive and tied to the verbose old format. It now uses at most 128 sampled stars and 128 sampled worlds, includes shared-format costs, and leaves every generated object and random draw intact. The duration is recorded after the estimate. The previously timing-out fictional preview regression now completes within its deadline in the latest full run.

8. I overgeneralized verification results.

The earlier tests established several useful invariants: output equality for a local change, deterministic geometry or population digests, correct cache invalidation for tested cases, and particular rendering checks. They did not establish that realistic saves were reasonably sized, that all horizon workloads were fast, or that remote fictional zones with many planets and moons had been profiled adequately.

Likewise, passing rendering checks does not prove good frame time. A regression test can validate pixels, labels, or geometry while a scene remains slow. A performance report must state which workloads were measured, which paths were inspected only, which options were disabled, and what was not exercised.

Hardware-counter profiling was restricted on this machine. That limits particular measurements, but Callgrind, wall-clock timing, source inspection, file attribution, and memory measurements were available. The restriction did not prevent discovering the JSON duplication. It is not a valid explanation for missing it.

The final audit message should have said that the recorded findings were resolved, while leaving comprehensive coverage unclaimed. Instead, it conveyed a level of completion the methodology did not support.

9. What the subsequent fix actually establishes.

The current galaxy archive is 698,455,272 bytes. Its separate compact copy is 119,418,692 bytes, approximately 83% smaller. The original archive is unchanged. Both contain the same 126,874 saved objects; the optimization does not obtain its reduction by deleting stars, planets, moons, companions, or favorites.

Version 2 uses short keys, shared class/orbit defaults, shared generation batches, and exact shared spatial frames. It omits unused reports and per-record defaults, reconstructs generated system metadata only where the implication is exact, and preserves explicit clearing edits. Fictional metallicity uses numeric ratio codes and compact provenance, without invented observational error bars. Fictional iron abundances remain eligible for the model as exact assigned values; real-star uncertainty and source checks remain in place.

Common display/material values are rounded to four decimal places, with protection for tiny nonzero values. Spatial data, timing, motion, density inputs, seeds, and physical-evidence enums retain precision. The format preserves older saves and individual-body imports.

A conversion check compared the retained physical and provenance inputs for every record. Separate complete imports at one fixed simulation epoch produced identical positions and planes, orbital data, masses and radii, classes, parent links, fictional identities, planet/HZ counts, and favorites across all 126,874 records. This is strong evidence for this actual dataset, not a proof covering every imaginable future record.

All 73 serialization checks pass, including malformed-header/reference rollback, meaningful zero values, explicit false edits, literal metadata keys and arrays, atmosphere semantics, fictional identities and motion, favorites, and metallicity eligibility. The sanitizer memory-access run also passes those 73 checks; leak detection was disabled for these fixtures. Both Make and CMake builds pass.

The broad 685-check run has 673 passes, six optional GPU skips, and six known/configuration exceptions: the five existing disabled-condensation expectations and a host-count fixture still expecting 10% while the preserved local configuration is 33.3%. The serialization changes did not silently change that user setting to make the old assertion pass.

10. Size reduction and load-time reduction are different results.

In a headless full-file harness containing a Sun plus the entire saved population, current legacy/compact JSON parsing took approximately 12.54/3.89 seconds. With the current reference-based readers, complete imports took 36.17/33.63 seconds respectively. The remaining object creation, hierarchy resolution, physical updates, and bookkeeping are substantial.

Using the same compact file, the former copying reader took 42.41 seconds versus 33.63 seconds for the reference-based reader. An earlier pre-change legacy import took 51.65 seconds. The current legacy/compact harness's peak RSS was 3,431,392/1,667,668 KiB.

These are local measured runs, not universal speed promises. The harness does not include a full GUI startup with all catalog objects and rendering. It also performs a separate parse before the import measurement, so its peak-process figures describe that harness. In particular, an 83% file-size reduction is not an 83% reduction in total startup time. The remaining costs are part of the replacement audit's proposal inventory.

11. What changes in the replacement audit.

The frame-rate review is tied to the fixed code baseline and explicit scenes, including the populated remote galaxy archive, a wet vegetated horizon, camera movement, and walking. It follows the complete main-loop path rather than stopping at draw_horizon or at one named optimization.

It inventories catalog-wide scans, active-system selection, astrometry and projection, eclipse/light-source work, sky backgrounds, terrain sampling and rasterization, biome/coastline queries, vegetation generation/projection/drawing, water geometry and glints, clouds/rain, GPU uploads/readbacks, UI work, allocations, worker contention, pacing, and memory pressure.

The proposal report labels observed source behavior, measured costs, and unmeasured hypotheses separately. Compile-time optional paths are identified as optional; a disabled GPU branch is not presented as the cause of the current default frame rate. Native frame timing and instrumented instruction traces are not mixed into one apparent FPS number. Software-renderer results are identified as such.

The user has explicitly invited aggressive cuts. The proposal list therefore includes visible tradeoffs as well as behavior-preserving optimizations: density/range budgets, reduced detail, slower update cadences, reduced sampling, and disabling particular effects. Each such proposal states what can change or disappear and which acceptance behavior would have to be reconsidered. None of those cuts is implemented by the audit.

The list is also a review artifact, not a promise that every candidate is a bottleneck or that their benefits add together. Overlapping proposals are identified, small opportunities are ranked below major recurring work, and verification plans accompany the recommendations.

The corrective lesson is straightforward: audit actual data and actual workloads, follow writers through readers and callers, attribute the complete cost, and make coverage claims no broader than the evidence. The user should not have had to discover this serialization problem after an audit described as exhaustive.
